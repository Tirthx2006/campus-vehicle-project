## Overview

Campus Vehicle is a student-built, real-time ride-sharing platform designed for university communities (currently configured for Ganpat University, Gujarat). Users can act as either passengers or verified drivers. The system supports two distinct ride modes:

- **Quick Drop** — on-campus, short hop rides (driver goes online, passenger pings them directly)
- **Route Share** — long-distance rides where a driver publishes a route and passengers book seats and split the fare

All real-time coordination (request flow, acceptance, GPS tracking, payment requests, ride events) is delivered via **Socket.io** instead of polling. The frontend is a single-page application (SPA) rendered entirely client-side.

```
┌───────────────────────────────────────────────────────┐
│              Browser (index.html + script.js)          │
│  SPA with page-switching via show/hide CSS classes     │
├───────────────────────────────────────────────────────┤
│        Socket.io Client (cdn.socket.io)                │
│        Leaflet Maps  (Nominatim + OSRM routing)        │
├───────────────────────────────────────────────────────┤

├───────────────────────────────────────────────────────┤
```

## Components

### Backend (`backend/index.js`)
- **Purpose:** Single-file Express + Socket.io server. Handles all auth, business logic, real-time events, and DB operations.
- **Location:** `backend/index.js`
- **Entry point:** `node index.js` (port 5000; or `process.env.PORT` for Render.com)
- **Key responsibilities:**
  - JWT issue (login) and validation (`auth` middleware on protected routes)
  - `emergencyAuth` — query-param token variant for `sendBeacon` (tab-close cleanup)
  - Socket.io authenticated connections: joins each user to their email-keyed room
  - GPS telemetry forwarding (driver → accepted passengers)
  - All REST endpoints listed below

### Frontend SPA (`frontend/`)
- **Purpose:** Single HTML file + CSS + JS. No build step. SPA pattern with `hidden` CSS toggling between "pages".
- **Location:** `frontend/index.html`, `frontend/script.js`, `frontend/styles.css`
- **Key responsibilities:**
  - Auth flows: signup, login, JWT storage in `localStorage`
  - Role selection (Passenger / Driver) with sub-mode selection (Quick Drop / Route Share)
  - Map initialization via Leaflet (open-source, no API key needed):
    - Nominatim geocoding for autocomplete
    - OSRM for routing polylines + ETA
    - Interactive tap-to-select destination map (passenger)
    - Live driver location marker (passenger tracking)
    - Route preview map (driver publish form)
    - Command Center live map (driver)
  - Real-time socket event listeners for the full ride lifecycle
  - Toast notification system (custom, no native `alert`)
  - Custom confirm dialog (replaces native `confirm()`)
  - Pickup location modal
  - Trip history page (`My Activity`)

### Ride Status State Machine

**Route Share Ride (`rides.status`):**
```
active → in_progress → payment_pending → (deleted on complete/cancel)
```

**Route Share Request (`rides.requests[].status`):**
```
pending → accepted → arrived → paid
```

**Quick Drop (`quick_requests.status`):**
```
pending → accepted → arrived → in_progress → payment_pending → completed | rejected
```

## Data Flow

### Route Share (Driver perspective)
1. Driver publishes route → `POST /publish-route` → new `Ride` doc created
2. Passenger requests seat → `POST /request-ride` → `new_request` socket event fires to driver
3. Driver accepts → `POST /accept-passenger` → `ride_accepted` socket event fires to passenger
4. Driver marks arrival → `POST /arrive-passenger` → `driver_arrived` fires to passenger
5. Driver starts → `POST /start-route` → `ride_started` fires to all accepted passengers
6. Driver requests payment → `POST /request-payment` → `payment_requested` fires to all
7. Passenger confirms → `POST /passenger-paid` → `passenger_paid` fires to driver
8. Driver completes → `POST /complete-route` → `ride_completed` fires to all; Ride doc deleted

### Quick Drop (Driver perspective)
1. Passenger finds online driver → `GET /search-campus-drivers` → public
2. Passenger requests → `POST /request-quick-drop` → `new_quick_request` fires to driver
3. Driver accepts → `POST /accept-quick-drop` → `quick_drop_accepted` fires to passenger
4. Driver arrives → `POST /arrive-quick-drop` → `quick_drop_arrived` fires to passenger
5. Driver starts drop → `POST /start-quick-drop` → `quick_drop_started` fires to passenger
6. Driver requests payment → `POST /request-quick-payment` → `payment_requested` fires
7. Passenger confirms → `POST /passenger-paid` (type=quick_drop) → `passenger_paid` fires
8. Driver completes → `POST /complete-quick-drop` → `quick_drop_completed` fires to passenger

## Technical Debt

- [ ] **Monolithic backend:** All 1015 lines in a single `index.js` — needs splitting into route files and a controller layer
- [ ] **No tests:** Zero automated tests (backend or frontend)
- [ ] **No dev dependency / build tooling:** No nodemon, no eslint, no formatter configured
- [ ] **Quick Drop fare hardcoded:** `fare: 10` is hardcoded in `/request-quick-payment` — should be dynamic
- [ ] **No input sanitization:** Minimal server-side validation beyond auth; no schema-level validation library (Joi/Zod)
- [ ] **Ride history incomplete:** `my-trips` only queries `Ride` not `QuickRequest` — quick drop rides are missing from history
- [ ] **No rate limiting:** Any endpoint can be hammered; no express-rate-limit
- [ ] **No logging framework:** Only `console.log/error` — no structured logging (Winston/Pino)
- [ ] **`my-trips` defined after `server.listen`:** Route registered after server starts — works but is a structural smell
- [ ] **Google/Apple social login buttons:** Present in UI but unimplemented (no OAuth flow)
- [ ] **Settings toggles not persisted to backend:** Only saved to `localStorage`
- [ ] **Recent trips hardcoded on home page:** "UVPCE", "MB UVPCE", "HOSTEL" are static HTML, not real history

## Conventions

**Naming:** camelCase functions, kebab-case element IDs, SCREAMING_SNAKE_CASE for config constants  
**Structure:** Flat; all frontend in `frontend/`, all backend in `backend/`  
**Auth pattern:** JWT Bearer token — stored in `localStorage`, sent as `Authorization: Bearer <token>` header; Socket.io uses `auth.token` handshake  
**Real-time philosophy:** Event-push first (no polling); page refreshes use dedicated REST snapshot endpoints (`/get-active-mission`, `/my-ride-status`)  
**Testing:** None  
**Error handling:** `try/catch` on all async routes; client shows toast on failure
